# ADR-0008: Caller-supplied strings are length-prefixed inside composite Redis keys

**Status:** Accepted

## Context

Several Redis keys are built from more than one caller-supplied string — most notably `concurrency:{target}:{budgetKey}`, which combines a `target` (convention: `"provider:model"`, e.g. `"groq:llama-3.3-70b-versatile"`) and a `budgetKey` (an arbitrary caller-chosen string) into one key.

If these are joined with a plain `:` separator, the composite key is ambiguous: `target = "a:b", budgetKey = "c"` and `target = "a", budgetKey = "b:c"` both naively serialize to the same string, `concurrency:a:b:c`. Since `target` strings are expected to *routinely* contain colons (that's the documented naming convention), this isn't a theoretical edge case — it's close to the common case.

A collision here means two genuinely unrelated (target, budgetKey) pairs would silently share one concurrency counter, directly violating Invariant 13 (two unrelated agent trees sharing no `budgetKey` must never affect each other's admission outcomes).

## Decision

Every caller-supplied string segment used inside a composite key is wrapped with its own length prefix before concatenation: `seg(value) = "${value.length}:${value}"`. So `concurrency:{target}:{budgetKey}` is actually built as `concurrency:${seg(target)}${seg(budgetKey)}`, which for `target="a:b", budgetKey="c"` produces `concurrency:3:a:b1:c` and for `target="a", budgetKey="b:c"` produces `concurrency:1:a3:b:c` — distinct strings, because the length prefix makes the segment boundary unambiguous regardless of what characters the segment itself contains.

This applies everywhere a composite key mixes more than one caller-supplied string: currently `concurrency`, `budget`, `retries`, and `circuit`. Keys built from exactly one caller-supplied string, or from broker-issued UUIDs (which are never adversarially chosen and don't need this treatment), are left as plain concatenation.

## Alternatives considered

- **Escape colons in caller input before joining.** Rejected: now every escaping scheme has to handle the escape character appearing *in* the input too (what if `target` itself contains the escape sequence?), which is the same unbounded-ambiguity problem one level deeper, not actually solved.
- **Reject `:` in caller-supplied `target`/`budgetKey` values entirely.** Rejected: this directly conflicts with the documented `provider:model` convention for `target`, which is exactly the shape users are expected to supply. Banning the character that the convention recommends is a worse trade than solving the ambiguity structurally.
- **Use a non-printable or otherwise "safe" separator character instead of relying on length prefixing.** Rejected for the same reason as escaping: any fixed separator can, in principle, appear in caller input unless actively forbidden, which reopens the same problem one layer down. Length-prefixing sidesteps this because the prefix is parsed by position, not by scanning for a delimiter character at all.

## Consequences

- This is specifically and directly unit-tested: `keys.test.ts` asserts that a colon moving between `target` and `budgetKey` produces different concurrency keys, and separately asserts that a grid of adversarial-looking strings (`""`, `":"`, `"::"`, `"a:"`, `":a"`, etc.) all produce pairwise-distinct keys when combined.
- Every new composite key added to `redis/keys.ts` in the future must use `seg()` on each caller-supplied segment — a plain template-literal join is the bug this ADR exists to prevent from being reintroduced.
- Broker-issued identifiers (`agentId`, `reservationId`) are UUIDs and are deliberately *not* wrapped in `seg()` — they're generated by this library, not supplied by a caller, so there's no adversarial input to guard against for those segments, and skipping the prefix keeps those keys more readable in `redis-cli` during debugging.
